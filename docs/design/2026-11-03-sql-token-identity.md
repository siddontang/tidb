# Native SQL Token Identity for TiDB

Tracking: [feature Issue #4](https://github.com/siddontang/tidb/issues/4), [prototype PR #3](https://github.com/siddontang/tidb/pull/3). Status: implementation in progress; no new runtime authentication capability is enabled. Baseline: `30d6b0e7e5a993e0b15a32e923a0a576ad70aa8e`. The companion [ExecPlan](2026-11-03-sql-token-identity-plan.md) defines the implementation and verification sequence. This document defines a generic kernel capability for self-managed TiDB, TiDB X and hosted services. Identity-provider login, token issuance, KMS and fleet distribution belong to deployment adapters. These deployment variants describe the contract and unit-test coverage, not verified runtime support.

## Outcome and boundaries

A user or service authenticates to its organization's identity system, obtains an explicitly authorized database token from a broker, and connects with a MySQL-compatible client over verified TLS. TiDB validates an exact operator-defined database audience and an active binding to a native SQL account. Native SQL grants still decide which statements are allowed. Removing the binding or disabling the principal must deny new connections and terminate affected existing sessions under a declared policy lease once the pending lifecycle implementation is complete.

The kernel does not depend on a particular service platform, account hierarchy, principal taxonomy, username convention, API endpoint or identity provider. It does not accept arbitrary OIDC ID/access tokens: the broker adapts its identity model into one fixed, strict SQL-token profile. Management administrator status never implies a native SQL grant. Signing and policy distribution remain outside the SQL request path. Public/private networking affects reachability, not database identity.

This branch contains an isolated stateless verifier and a legacy native-wire test. It does not enable new-profile login, deployed resource scoping, active-session revocation or a changed running TiDB binary. Existing password plugins and `tidb_auth_token` keep their behavior. The proposed opt-in server profile is `tidb_sql_token_v1`, with `typ=tidb-sql+jwt`; neither is registered as available SQL syntax/configuration. Earlier draft profiles were never registered; this document defines the current proposed contract.

## Kernel and adapter responsibilities

| Generic TiDB responsibility | Deployment adapter responsibility |
|---|---|
| Validate signature, issuer, exact audience, explicit native binding and bounded token/session policy | Authenticate to the identity provider, authorize token exchange and mint the fixed SQL profile |
| Bind `(issuer, principal_id)` to exact native `(user, host)` and independent grant-readiness revisions | Map external user/service identities and directory entries into opaque stable principals |
| Compare trusted request storage scope to the trusted policy target | Install an authenticated audience-to-storage descriptor and attest the actual codec/storage cluster |
| Consume local public keys and expiring policy; later enforce activation, revocation and session guards | Select KMS/HSM/signing implementation, distribute snapshots and reconcile explicit native users/grants |
| Preserve native MySQL transport and SQL privilege checks | Choose resource names, role mappings, product placement and operational rollout |

For example, one operator can configure `urn:example:database:orders` for a cluster, while another can choose `urn:example:database:tenant-42` for a tenant keyspace. Both are opaque audience strings to TiDB. Replacement processes retain a stable audience only for the same logical database, with an updated trusted storage descriptor and process incarnation. External authorization changes must be translated into SQL-binding policy changes; browser logout and SQL-session revocation remain separate events. Identity-provider passwords are never copied into TiDB.

Existing legacy token integration establishes the reusable native boundary: issuer/key verification, native account selection and native SQL grants. Add scope and lifecycle semantics through the new profile while preserving existing token behavior. Protocol definitions, implementation dependencies, acceptance and discussion are available in this repository and the linked public Issue.

## External issuer integration

An operator-approved issuer is any service capable of producing this fixed signed profile after authenticating a principal and authorizing database access. It may be an existing identity platform with an adapter, a service-identity broker or an operator's own token service. TiDB does not require a specific vendor SDK, token-exchange URL or account taxonomy. An arbitrary identity-provider access/ID token is not automatically a database token; an adapter exchanges it when its format or audience differs.

The intended onboarding contract is:

1. **Establish trust out of band.** The operator installs the exact issuer identifier, its public verification keys and bounded policy through authenticated delivery. The signing key stays with the issuer. `iss`, `kid`, embedded keys and URLs in an incoming token cannot establish trust. This prototype has one issuer per policy snapshot; simultaneous multi-issuer routing/selection is not implemented.
2. **Bind the database target.** Assign a stable opaque audience and install its storage descriptor. The receiver must attest actual storage-cluster and codec/keyspace scope. A client-supplied audience never chooses a trusted target.
3. **Provision explicit SQL authorization.** Map immutable `(issuer, principal_id)` to a native `(user, host)` account in token mode, apply its native SQL grants, and publish an enabled expiring binding only after the intended grant revision is verified. Directory groups and management roles are translated by the adapter and are not SQL privileges by themselves.
4. **Issue the fixed token.** Authorize exchange for the exact audience/binding, set the twelve claims below, and sign with the already-published key. For example, `iss=https://issuer.example.invalid`, `aud=urn:example:database:orders`, `sub=sql_user`, and `principal_id=employee:42` are independent values. The MySQL username matches `sub`; the immutable external principal is not substituted for it.
5. **Connect and enforce lifetime.** A MySQL-compatible client presents the token through `mysql_clear_password` after certificate- and hostname-verified TLS. Native integration must reject plaintext before requesting the token, activate a connection guard before SQL execution, and enforce native grants. The current prototype has no registered plugin or connection guard, so this is the integration target rather than an executable setup recipe.
6. **Operate keys and policy.** Publish keys before issuing tokens and observe receiver acknowledgement. Publish authorization removals with newer revisions, distinguish ordinary key rotation from emergency session revocation, and bound disconnected receivers by policy expiry. Neither refresh failure nor restart permits a fresh lease from stale cached authorization.

The implemented Go boundary is `VerifySQLToken(raw, request, policy, now)`, backed by `SQLTokenRequest`, `SQLTokenPolicy` and `SQLTokenBinding`. It is an internal verifier seam, not a public issuer-management API. Trusted storage/account discovery, policy-file serialization and installation, receiver acknowledgements and token-exchange endpoints remain adapter/runtime work. Their transport must preserve the contract above; no operational HTTP API or SQL syntax is introduced by this design increment.

Acceptance requires an independently configured external issuer, its own audience/principal namespace, a deployed receiver and a stock MySQL client. Verify authorized SQL, cross-resource and cross-issuer denial, key rotation, policy outage/restart and held-session revocation. The existing unit fixtures and legacy wire test do not satisfy that complete integration gate.

The existing extension API in `pkg/extension/auth.go` is a useful entry point, but `AuthenticateUser` returns only `error`. It has no verified-claims carrier or complete session-lifetime contract. Adding an extension alone cannot solve reset, migration or held-session revocation. Prefer a small explicit native feature with an independent identity type; avoid changing every custom extension's existing function signature.

## Trusted database target

`sessionauth.Target` contains an opaque `Audience`, nonzero `StorageClusterID`, explicit `StorageScope` and `KeyspaceID`. Scope zero and unknown values are invalid. `StorageScopeCluster` represents an unkeyspaced/API-v1 cluster and uses canonical keyspace zero; the trusted adapter must first identify the actual codec and normalize its API-v1 null sentinel. `StorageScopeKeyspace` represents API-v2 and accepts numeric IDs from zero through `0xFFFFFF`. API-v2 DEFAULT (zero) is distinct from cluster scope because the explicit scope differs. Do not infer mode from a numeric keyspace value.

A trusted operator/agent installs the audience-to-storage descriptor with trust-domain and descriptor-generation metadata. Before admitting tokens, the adapter checks `kv.Storage.GetClusterID()` and the actual codec/mode/keyspace identity, and excludes reserved scopes according to deployment policy. In TiDB X, reject SYSTEM by its actual name/classification and admit only designated customer keyspaces; SYSTEM can have a positive ID, and numeric range checks cannot identify it. Supporting DEFAULT in the generic verifier does not authorize an adapter to expose it against deployment policy. Empty descriptors, unsupported codec/mode, missing scope or actual/request/policy mismatches fail closed.

Audience equality is byte-exact; the kernel does not prepend a prefix, infer organization or interpret a service-specific resource identifier. The same audience must not be assigned to unrelated databases in one issuer trust domain. Keys and native usernames can be shared, so they do not establish resource isolation. Request and policy targets must agree in every field, including storage cluster, scope and keyspace. Keyspace IDs can repeat in different storage clusters.

The first runtime integration supports one trusted database target per SQL process, matching the inspected single configured-keyspace path. A process serving several targets would require a separately reviewed trusted routing context and policy namespace per connection. Deployment changes retain a stable audience only for the same logical database and use fresh process incarnations. Cross-trust-domain movement requires explicit issuer/key handover.

Clients cannot set the descriptor through SET, connection attributes, user metadata, URI parameters or the token being verified. Its authority is operator policy, independent of token signing. The initial transport should be a tightly permissioned local file installed by an authenticated operator/agent, with no unauthenticated status endpoint. Descriptor validation and delivery are not implemented in this stateless increment.

## Versioned authentication contract

Use the maintained JWS implementation already in TiDB for signature verification. Bound the compact authentication payload before parsing. Reject duplicate JSON fields, malformed types, unsupported critical headers, remote key URLs and algorithm substitution. Resolve `kid` only within the configured issuer's local trusted key set; no incoming key or URL establishes trust.

The proposed protected header has exactly `alg=RS256`, `typ=tidb-sql+jwt`, and nonempty `kid`. Exactly twelve mandatory claims follow:

| Claim | Meaning and check |
|---|---|
| `ver` | Integer `1`; no legacy or arbitrary OIDC fallback |
| `iss` | Exact configured nonempty issuer |
| `aud` | One exact nonempty audience matching the trusted descriptor; no list, wildcard expansion or prefix matching |
| `sub` | Exact native username selected by MySQL account matching and the binding |
| `principal_id` | Opaque immutable principal in the issuer namespace; distinct from the native username and mutable email |
| `binding_id`, `binding_revision`, `policy_revision` | Active binding and authorization generation; revisions are canonical positive unsigned decimal strings |
| `iat`, `nbf`, `exp` | Canonical integer Unix seconds, required ordering and maximum lifetime; expiry is exclusive |
| `jti` | Bounded nonempty audit correlation ID, not proof of one-time use |

Organization/project, email, human/workload classification, roles and product tier are not claims in this profile. Unknown fields are rejected rather than silently receiving authorization meaning. Adapters retain product metadata outside this token. `sub` remains the exact native SQL username; `(iss, principal_id)` is the immutable identity namespace. SQL grants come from native records, never a token role list. A `(issuer, kid)` pair must not be reused for different key material.

The compact token is at most 16 KiB. Audience, principal/binding/token/key IDs, native names and host patterns are 1–256 printable ASCII bytes without whitespace; issuer is 1–1024 such bytes. These are v1 interoperability limits, not unrestricted TiDB username support. Revisions fit positive `uint64` with no sign or leading zero. NumericDate values are nonnegative integer Unix seconds through UTC year 9999. Initial clock skew is zero: `iat <= nbf < exp` and `iat/nbf <= now < exp`. Configured token lifetime is in `(0, 15 minutes]` and maximum session duration in `(0, 24 hours]`. Binding expiry is mandatory. RSA uses RS256, a positive odd 2048–8192-bit modulus and an odd exponent in `[3, 2^31-1]`.

`pkg/privilege/privileges/sql_token.go` owns the proposed plugin/type/version, custom-claim constants and named profile bounds/counts. Standard names reuse `jws.*Key` and `jwt.*Key`; the algorithm reuses `jwa.RS256`. `sessionauth.StorageScope` supplies typed scope constants. Existing plugin references reuse `mysql.AuthTiDBAuthToken` and related native constants. A signed literal golden fixture independently pins the twelve-field wire contract: changing production and fixture-builder constants together cannot silently change v1. Literal malformed/negative fixtures intentionally remain literal. The proposed plugin is not added to parser-supported plugins or runtime registration in this increment.

`VerifySQLToken(raw, request, policy, now)` consumes an already-authenticated immutable policy and trusted actual-storage/native-account facts. It validates signatures and exact scope/binding equality but does not establish provenance, query grants, prove freshness after restart or guard a session. Equal positive desired/applied native-grant revisions are generic readiness epochs; any trusted operator can publish them after verifying grants, without prescribing a particular reconciliation service. The returned secret-free value contains no token, key or mutable references and cannot serve as a live authorization guard.

Provision distinct native usernames for password and token modes, with collision detection, without prescribing their naming format. The trusted provisioning adapter chooses the mapping and creates token accounts only after explicit authorization. Managed authorization fields stay in authenticated policy, not self-editable user attributes. Native account existence/host matching and current lock/plugin checks remain mandatory. Classify managed token usernames before authentication-path selection: a changed plugin or competing host record must fail rather than fall back to an unguarded password account. Test self-service ALTER USER paths; policy refresh and reconciliation must retain managed-account classification during revocation.

## Policy snapshots and revocation

A snapshot contains the descriptor generation, opaque audience and actual storage-cluster/scope/keyspace IDs, monotonically increasing snapshot revision, `valid_from`/`valid_until`, accepted profile versions, issuer-scoped verification keys, and active bindings. Each binding names principal, native `(user, host)`, binding/policy revisions, expiry and verified native grant revision. A native role change is not authorized by the JWT itself. Install complete snapshots atomically after validating their producer, integrity, scope and structure.

The operator/broker owns policy and keys; the kernel is a consumer. Adapter delivery must preserve a persisted anti-rollback watermark across restart. Within a process, an older revision is rejected; the same revision is accepted only for identical content. Reusing an expired snapshot does not renew its validity. Removing a binding/key/principal is revocation; restoring it requires an increased authorization revision. Reintroducing a previously revoked binding with its old revision must not resurrect an old token or session. Retained tombstone/high-water state or an equivalent authoritative protocol is required, including after restart.

A malformed refresh must never replace a valid current snapshot with partially parsed state. The last known snapshot may be used only until its signed/trusted expiry, not forever. A failed refresh cannot extend authorization. Start with no token admission until a valid snapshot and native capability are ready. Clock rollback must not extend an installed lease: convert accepted wall-clock expiries into bounded monotonic process deadlines and retain restart watermarks. Persist time/expiry and revocation high-water evidence as well as revisions. On restart, cached files alone cannot establish freshness: require a fresh authority attestation bound to the new process incarnation/nonce and trusted time, with authorization no later than the underlying source policy expiry. If trusted time/freshness cannot be established, deny token admission and do not create a new full lease from cached state. A wall clock later than its previous watermark still does not prove that an old lease is unexpired. Test restart after expiry with clock rollback, as well as clock jumps/skew while running.

A snapshot-install transaction publishes the new revision and re-evaluates registered sessions. New-login activation checks and registration synchronize with this same publication boundary. No connection may verify against revision N, miss the N+1 revocation sweep, and later activate under N. Do not hold the publication lock during network I/O, SQL execution, or session cleanup. Under the lock, publish state and mark affected guards terminal before any subsequent dispatch-admission check can succeed; dispatch admission follows the same publication ordering. Collect cancellation candidates under that lock; outside it, cancel only the matching connection incarnation/auth generation, then observe completion. Work admitted before that publication is in flight and subject to native cancellation semantics, not retroactively unadmitted. A generation prevents a delayed callback from killing a newly authenticated user on the same connection only when check-and-terminate is atomic: under the same connection-auth synchronization used by CHANGE USER activation, verify the expected incarnation/generation and claim terminal connection shutdown. If replacement won first, the obsolete callback is a no-op; if shutdown won first, replacement cannot activate. Network cancellation runs afterward outside locks. A separate generation comparison followed by `Server.Kill(id)` is insufficient because reauthentication can occur between them.

Keep Identity-provider browser-session invalidation separate from SQL-policy revocation. Ordinary browser logout does not automatically revoke an established independent SQL session. Disabling a principal, removing its membership/data grant, emergency key retirement and database resource deletion do update the SQL policy. Normal signing-key rotation distinguishes “not accepted for new authentication” from “revoke existing sessions”: an old token naturally expires, but a session may outlive that token. Retain explicit verification/retirement metadata or require session draining before final key removal; emergency retirement must target existing sessions by issuer/key as well as principal/binding.

## Authentication result and connection guard

Use an immutable, secret-free identity type in a dependency-light package such as `pkg/sessionctx/sessionauth`. That package must not import `session`, `server`, `variable` or `privilege`, avoiding cycles. Fields include opaque audience/storage-cluster/scope/keyspace identity, issuer-scoped principal, binding/native user, authorization revisions, issuer/trust domain/key ID/profile, token ID, verification snapshot revision, login time and absolute maximum session deadline. Do not retain the original token.

Proposed additions, not existing APIs:

    privilege.VerificationInfo.AuthenticatedIdentity *sessionauth.Identity
    variable.SessionVars.AuthenticatedIdentity *sessionauth.Identity
    variable.SessionVars.SessionAuthorization sessionauth.Authorization
    clientConn.authGuard *connectionAuthGuard

The verifier creates the identity after cryptographic and native-record checks. `session.Auth` publishes it only after all existing account-lock/password-state/default-role steps succeed. SessionVars holds a read-only view for audit and authorization; the connection guard is the lifetime authority. Internal sessions without a public authenticated identity do not acquire one through reset or session-state decoding.

The dependency-light `sessionauth.Authorization` interface exposes `Check() error` on the shared guard without importing server code into session/variable. A session with a token identity but no guard fails closed. Only a nil identity for a legacy/internal session retains existing behavior; toggling `InRestrictedSQL` does not bypass a token guard.

The guard holds connection incarnation, authentication generation, immutable identity, maximum session deadline, current policy-lease deadline and a terminal revoked flag. SQL permission checks remain native and must not be replaced by the token role list. Check the guard both before server command dispatch and at `session.ExecuteStmt` and `PrepareStmt` entry, including callers such as init-connect that can execute outside normal dispatch. Check every statement of a multi-statement request, not only its initial packet. `ExecutePreparedStmt` delegates to `ExecuteStmt`, while cursor FETCH in `pkg/server/conn_stmt.go` directly consumes a result set and needs the dispatch check plus cancellation during streaming. A helper that uses a token-authenticated session must retain its guard and exact storage scope. The cross-keyspace session pool in `pkg/domain/crossks` must not copy token identity into a different store or discard the guard to run customer work as an unscoped internal principal. Explicit internal system work remains separately authorized and audited; `InRestrictedSQL` alone does not authorize such a transition. A server-owned lease scheduler wakes idle sockets and active commands when needed. Checking only before the next statement would leave idle connections and running queries authorized indefinitely.

Do not represent revocation solely through `SQLKiller.Signal`: dispatch resets that field. Terminal guard state prevents further work even if query state resets. Integrate with `Server.Kill`/`killQuery` mechanisms to set shutdown state, wake socket reads and writes, cancel dispatch and signal execution. Cleanup remains with the normal connection owner so concurrent transaction/session mutation is avoided. Collect callbacks without holding policy/registry locks; observe connection exit and record incomplete cancellation.

Three time policies are separate: token validity controls new login; maximum session lifetime bounds an established login; policy lease bounds offline authorization and revocation propagation. Refreshing a policy snapshot may refresh the lease only for the same still-authorized identity and cannot extend its maximum session lifetime. Token expiration alone need not close a session under this design. Examples such as a five-minute token are experiment parameters, not customer guarantees.

## Reset, change-user and migration

RESET CONNECTION retains the transport identity. Validate its guard before replacing the session context. Introduce a typed trusted restore path for token identities rather than calling the existing `AuthWithoutVerification`, which rematches username/host and checks only existence. Restore only the previously verified exact native `(user, host)` after validating its current plugin, lock/account state, binding/native-grant readiness and actual storage scope. A newly added more-specific host record must not change the selected grants during reset. Transfer only the existing verified identity and original deadline, and revalidate native-record and policy generations under the activation protocol before returning success. Failure is terminal for this token connection rather than a fallback to an unguarded session. Clearing user variables, prepared statements or temporary tables must not clear security state.

CHANGE USER is new authentication. Keep the old guard active while staging the new identity. On failure restore both old context and guard, without refreshing the old deadline. On success validate and atomically install the new guard generation before retiring the previous one. A stale old timer cannot revoke the new generation; an expired old guard cannot be revived by a failed change-user. Tests cover token-to-token, token-to-password and password-to-token transitions with the managed-account policy.

Initially reject session migration for the new plugin in both directions: prevent SHOW SESSION_STATES from issuing a migration credential for a token-bound identity, and reject `AuthTiDBSessionToken` when the matched native record is token-bound. Do not rely only on a server-side issuance check because a previously issued migration token may still exist. SET SESSION_STATES remains SQL session state, not authentication. Future migration requires a server-signed envelope bound to source/destination database audience and storage scope, original session deadline and authorization revisions, plus destination policy validation; it is a separate capability.

## Transactions and irreversible work

Revocation must prevent new commands, cancel interruptible work, close the connection and clean up an uncommitted transaction. It cannot undo acknowledged commits. A commit already past an irreversible point may finish while cancellation is in progress; DDL/background work may also outlive the connection. The current connection-liveness checker deliberately excludes COMMIT/ROLLBACK, DDL, ANALYZE, LOAD/IMPORT and some BR operations. Reusing that checker alone does not establish a security cutoff.

Define the initial guarantee as bounded denial of new admission and dispatch, plus observed session termination and best-effort cancellation through native execution semantics. Do not promise “no write after the revocation timestamp” or a hard bound on lock release for an in-flight noninterruptible commit. A stronger transaction-effect fence requires a separate kernel commit protocol and storage-level acceptance, not just connection closure. Audit disconnect outcome separately from transaction/job outcome. Native SQL roles should separately govern long-running administrative job submission; revocation does not silently delete an already accepted durable job.

## Rollout and acceptance

The new profile stays disabled by default. Enabling requires a valid descriptor, local policy, TLS, native capability support and verified token-account grants. Reject `skip-grant-table`/`SkipWithGrant` as an incompatible startup/readiness configuration for this feature: current `ConnectionVerification` returns early in that mode, before native/plugin checks. It must not yield a nil identity that silently falls back to unguarded legacy behavior. A rolling fleet routes token clients only to receivers acknowledging the profile and current key/policy revision. Unsupported builds fail explicitly; they do not fall back to legacy JWT or password. No new unauthenticated HTTP endpoint is needed. If a later authenticated internal endpoint is added under `pkg/server`, update `docs/tidb_http_api.md` in the same change.

Deliver in increments: an isolated existing-token feasibility experiment; strict v1 verifier and policy engine; typed identity/connection guard; reset/change-user/migration protections; then broker adapters and fleet rollout. Each integration increment must have real MySQL tests as well as unit tests. The detailed commands, negative oracles and readiness gates are in the ExecPlan. Until those pass, preserve existing password access and do not advertise the new SQL-token login profile.
