# Native Enterprise SQL Identity for TiDB X

Status: implementation in progress on `feature/enterprise-sql-identity`; no new runtime authentication capability is enabled. Baseline: `30d6b0e7e5a993e0b15a32e923a0a576ad70aa8e`. The companion [ExecPlan](2026-11-03-enterprise-sql-identity-plan.md) defines the implementation and verification sequence. This document concerns kernel support; Cloud login, token issuance, KMS and fleet distribution belong to the surrounding control plane.

## Outcome and boundaries

A customer authenticates to Cloud, obtains an explicitly authorized database token, and connects with a MySQL-compatible client over verified TLS. TiDB X validates that the token names this stable Instance and an active native database-access binding. Native SQL grants still decide which statements are allowed. Removing the binding or disabling the principal denies new connections and terminates affected existing sessions under a declared policy lease.

A token is not the Cloud password, and Cloud administrator status is not a SQL grant. Essential/Premium placement changes preserve the stable Instance identity. The kernel does not call the Global control plane or KMS on a SQL request. Public/private networking affects reachability, not database identity.

This branch defines implementation contracts, audits actual code paths, and now contains an isolated stateless verifier plus a legacy native-wire test. It does not claim new-profile login integration, deployed Instance scoping, active-session revocation, production readiness, or a changed running TiDB binary. Keep existing `mysql_native_password`, `caching_sha2_password`, and legacy `tidb_auth_token` behavior compatible. Introduce an explicitly selected versioned server plugin, provisionally `tidb_cloud_token_v1`; its name is not currently available SQL syntax or configuration.

The existing extension API in `pkg/extension/auth.go` is a useful entry point, but `AuthenticateUser` returns only `error`. It has no verified-claims carrier or complete session-lifetime contract. Adding an extension alone cannot solve reset, migration or held-session revocation. Prefer a small explicit native feature with an independent identity type; avoid changing every custom extension's existing function signature.

## Trusted Instance identity

A process may enable the first version only after an authenticated Cell Agent installs a deployment descriptor containing `instance_id`, expected storage-cluster ID and keyspace ID, deployment/Region trust domain, and descriptor generation. The process checks `kv.Storage.GetClusterID()` and the actual storage codec/keyspace identity before admitting token connections. An empty descriptor, SYSTEM keyspace, unexpected codec, or mismatched keyspace disables this feature with an explicit readiness reason. Keyspace IDs can repeat across storage clusters; a keyspace name or numeric keyspace ID alone is insufficient.

The first implementation supports one Instance binding per SQL process, matching the inspected single configured-keyspace path. If a future process serves several Instances, it needs a separate trusted routing context and policy namespace per connection; a global variable cannot be reused for that topology. Essential/Premium replacement processes receive the same stable Instance ID but fresh process-incarnation identity. Cross-Region changes require an explicit issuer/key handover.

Clients cannot set the descriptor via SET, connection attributes, SQL user metadata, URI parameters or a token claim. Its authoritative source is Region metadata. The Cell Agent installs a trusted local projection through a tightly permissioned file or authenticated internal channel. The first implementation should use a local file installed by the Agent to avoid adding an unauthenticated status endpoint. The descriptor trust root is independent of the token being verified.

## Versioned authentication contract

The broker issues a compact signed JWT with a strict profile. Reuse the repository's maintained JWS implementation for cryptographic verification; do not implement signature primitives. Bound the complete authentication payload before parsing. Accept one canonical header/profile, reject duplicate JSON keys, malformed types, unsupported critical headers, remote key URLs and algorithm substitution. Pin RS256 initially and resolve `kid` only inside the locally configured issuer/trust domain. Public verification keys come from the trusted snapshot, never from the incoming token.

Proposed header: `alg=RS256`, `typ=tidb-cloud-sql+jwt`, nonempty `kid`. Proposed mandatory claims:

| Claim | Meaning and check |
|---|---|
| `ver` | Integer `1`; no fallback to the legacy profile |
| `iss` | Exact configured nonempty issuer |
| `aud` | A single string `tidb-cloud:instance:<canonical Instance ID>` matching the trusted descriptor; wildcard, list and other Instances are rejected |
| `sub` | Exact native username selected by the MySQL handshake and the binding |
| `principal_id`, `principal_kind` | Immutable Cloud principal and human/workload kind; match the binding snapshot, never mutable email |
| `organization_id`, `project_id` | Match descriptor/policy scope |
| `binding_id`, `binding_revision`, `policy_revision` | Match active binding and principal authorization policy; revisions use canonical unsigned decimal strings to avoid JSON floating-point loss |
| `iat`, `nbf`, `exp` | Integer Unix seconds with enforced ordering, configured maximum lifetime, and bounded clock-skew policy; expiry is exclusive |
| `jti` | Bounded nonempty token ID for audit correlation; not proof of one-time use |

The canonical Instance ID is the existing stable resource identifier, compared byte-for-byte; token support does not rename it or require converting a local `inst-...` ID into a UUID. Exact validation limits must be frozen with the broker contract before either is enabled. Reject unknown profile fields in v1 rather than silently assigning them security meaning. Email may be audit/display metadata outside this authentication profile. The same `(issuer, kid)` may never identify different key material; rotation uses a new ID. Token-signature success is necessary but not sufficient: a current policy snapshot, active native user, exact binding and native grants are still required.

The first verifier increment fixes these prototype limits: complete compact token at most 16 KiB; exactly three protected-header fields and fifteen claims; identifiers, native names, host patterns, key IDs and token IDs use 1–256 printable ASCII bytes without whitespace; issuer uses 1–1024 such bytes. The audience adds the literal prefix to the bounded Instance ID. Revisions are positive `uint64` decimal strings with no sign or leading zero. NumericDate values are canonical nonnegative integer Unix seconds through year 9999; initial clock skew is zero, with `iat <= nbf < exp` and `iat/nbf <= now < exp`. Configured token lifetime is positive and at most 15 minutes; maximum session duration is positive and at most 24 hours. Binding expiry is mandatory. RSA verification uses only RS256 with a positive odd 2048–8192-bit modulus and an odd exponent in `[3, 2^31-1]`. The future broker must use this same contract before enablement.

`VerifyCloudToken` takes an already-authenticated immutable policy and trusted actual storage/native-account facts. It verifies signatures and compares values; it does not acquire their provenance, read native grants, install a snapshot, prove restart freshness or guard a SQL session. The caller must ensure actual storage matches the descriptor, reject SYSTEM by trusted keyspace name/classification, and pass the exact matched native record after account checks. Numeric keyspace ID zero is DEFAULT, not a reliable SYSTEM marker; nonzero IDs through `0xFFFFFF` only establish an allowed numeric API-v2 range. A SYSTEM keyspace can have a positive ID. This adapter is not yet implemented. The returned `sessionauth.Identity` contains no token or key and must not be used as a standalone live authorization guard.

Provision separate native usernames for password and token modes, derived from immutable Instance/principal IDs plus a managed auth-mode namespace, with collision detection. An opt-in rollout creates the token account; it does not change a retained password user's auth plugin. The control plane owns native user/grant reconciliation and reports a binding ready only when the intended native grant revision is verified. Cloud-controlled authorization fields are kept in the trusted policy snapshot, not in self-editable user attributes. Unprivileged SQL users must not alter their own plugin to escape the profile or obtain a migration credential; tests must cover available self-service ALTER USER paths. Native account existence and host matching remain mandatory. The trusted policy marks managed token usernames before choosing a native authentication path; a changed native plugin or competing host record for such a username is a readiness/authentication failure, not a reason to treat it as an unguarded password account. Policy refresh and account reconciliation must preserve this distinction even while a binding is being revoked.

## Policy snapshots and revocation

A snapshot contains the descriptor generation, stable Instance and actual storage-cluster/keyspace IDs, organization/project scope, monotonically increasing snapshot revision, `valid_from`/`valid_until`, accepted profile versions, issuer-scoped verification keys, and active bindings. Each binding names principal, native `(user, host)`, binding/policy revisions, expiry and verified native grant revision. A native role change is not authorized by the JWT itself. Install complete snapshots atomically after validating their producer, integrity, scope and structure.

Region owns policy and keys; the kernel is a consumer. Agent delivery must preserve a persisted anti-rollback watermark across restart. Within a process, an older revision is rejected; the same revision is accepted only for identical content. Reusing an expired snapshot does not renew its validity. Removing a binding/key/principal is revocation; restoring it requires an increased authorization revision. Reintroducing a previously revoked binding with its old revision must not resurrect an old token or session. Retained tombstone/high-water state or an equivalent authoritative protocol is required, including after restart.

A malformed refresh must never replace a valid current snapshot with partially parsed state. The last known snapshot may be used only until its signed/trusted expiry, not forever. A failed refresh cannot extend authorization. Start with no token admission until a valid snapshot and native capability are ready. Clock rollback must not extend an installed lease: convert accepted wall-clock expiries into bounded monotonic process deadlines and retain restart watermarks. Persist time/expiry and revocation high-water evidence as well as revisions. On restart, cached files alone cannot establish freshness: require a fresh authority attestation bound to the new process incarnation/nonce and trusted time, with authorization no later than the underlying source policy expiry. If trusted time/freshness cannot be established, deny token admission and do not create a new full lease from cached state. A wall clock later than its previous watermark still does not prove that an old lease is unexpired. Test restart after expiry with clock rollback, as well as clock jumps/skew while running.

A snapshot-install transaction publishes the new revision and re-evaluates registered sessions. New-login activation checks and registration synchronize with this same publication boundary. No connection may verify against revision N, miss the N+1 revocation sweep, and later activate under N. Do not hold the publication lock during network I/O, SQL execution, or session cleanup. Under the lock, publish state and mark affected guards terminal before any subsequent dispatch-admission check can succeed; dispatch admission follows the same publication ordering. Collect cancellation candidates under that lock; outside it, cancel only the matching connection incarnation/auth generation, then observe completion. Work admitted before that publication is in flight and subject to native cancellation semantics, not retroactively unadmitted. A generation prevents a delayed callback from killing a newly authenticated user on the same connection only when check-and-terminate is atomic: under the same connection-auth synchronization used by CHANGE USER activation, verify the expected incarnation/generation and claim terminal connection shutdown. If replacement won first, the obsolete callback is a no-op; if shutdown won first, replacement cannot activate. Network cancellation runs afterward outside locks. A separate generation comparison followed by `Server.Kill(id)` is insufficient because reauthentication can occur between them.

Keep Cloud browser-session invalidation separate from SQL-policy revocation. Ordinary browser logout does not automatically revoke an established independent SQL session. Disabling a principal, removing its membership/data grant, emergency key retirement and Instance deletion do update the SQL policy. Normal signing-key rotation distinguishes “not accepted for new authentication” from “revoke existing sessions”: an old token naturally expires, but a session may outlive that token. Retain explicit verification/retirement metadata or require session draining before final key removal; emergency retirement must target existing sessions by issuer/key as well as principal/binding.

## Authentication result and connection guard

Use an immutable, secret-free identity type in a dependency-light package such as `pkg/sessionctx/sessionauth`. That package must not import `session`, `server`, `variable` or `privilege`, avoiding cycles. Fields include stable Instance/storage-cluster/keyspace identity, principal/kind, binding/native user, authorization revisions, issuer/trust domain/key ID/profile, token ID, verification snapshot revision, login time and absolute maximum session deadline. Do not retain the original token.

Proposed additions, not existing APIs:

    privilege.VerificationInfo.AuthenticatedIdentity *sessionauth.Identity
    variable.SessionVars.AuthenticatedIdentity *sessionauth.Identity
    variable.SessionVars.SessionAuthorization sessionauth.Authorization
    clientConn.authGuard *connectionAuthGuard

The verifier creates the identity after cryptographic and native-record checks. `session.Auth` publishes it only after all existing account-lock/password-state/default-role steps succeed. SessionVars holds a read-only view for audit and authorization; the connection guard is the lifetime authority. Internal sessions without a public authenticated identity do not acquire one through reset or session-state decoding.

The dependency-light `sessionauth.Authorization` interface exposes `Check() error` on the shared guard without importing server code into session/variable. A session with a Cloud identity but no guard fails closed. Only a nil identity for a legacy/internal session retains existing behavior; toggling `InRestrictedSQL` does not bypass a Cloud guard.

The guard holds connection incarnation, authentication generation, immutable identity, maximum session deadline, current policy-lease deadline and a terminal revoked flag. SQL permission checks remain native and must not be replaced by the token role list. Check the guard both before server command dispatch and at `session.ExecuteStmt` and `PrepareStmt` entry, including callers such as init-connect that can execute outside normal dispatch. Check every statement of a multi-statement request, not only its initial packet. `ExecutePreparedStmt` delegates to `ExecuteStmt`, while cursor FETCH in `pkg/server/conn_stmt.go` directly consumes a result set and needs the dispatch check plus cancellation during streaming. A helper that uses a Cloud-authenticated session must retain its guard and exact storage scope. The cross-keyspace session pool in `pkg/domain/crossks` must not copy Cloud identity into a different store or discard the guard to run customer work as an unscoped internal principal. Explicit internal system work remains separately authorized and audited; `InRestrictedSQL` alone does not authorize such a transition. A server-owned lease scheduler wakes idle sockets and active commands when needed. Checking only before the next statement would leave idle connections and running queries authorized indefinitely.

Do not represent revocation solely through `SQLKiller.Signal`: dispatch resets that field. Terminal guard state prevents further work even if query state resets. Integrate with `Server.Kill`/`killQuery` mechanisms to set shutdown state, wake socket reads and writes, cancel dispatch and signal execution. Cleanup remains with the normal connection owner so concurrent transaction/session mutation is avoided. Collect callbacks without holding policy/registry locks; observe connection exit and record incomplete cancellation.

Three time policies are separate: token validity controls new login; maximum session lifetime bounds an established login; policy lease bounds offline authorization and revocation propagation. Refreshing a policy snapshot may refresh the lease only for the same still-authorized identity and cannot extend its maximum session lifetime. Token expiration alone need not close a session under this design. Examples such as a five-minute token are experiment parameters, not customer guarantees.

## Reset, change-user and migration

RESET CONNECTION retains the transport identity. Validate its guard before replacing the session context. Introduce a typed trusted restore path for Cloud identities rather than calling the existing `AuthWithoutVerification`, which rematches username/host and checks only existence. Restore only the previously verified exact native `(user, host)` after validating its current plugin, lock/account state, binding/native-grant readiness and actual storage scope. A newly added more-specific host record must not change the selected grants during reset. Transfer only the existing verified identity and original deadline, and revalidate native-record and policy generations under the activation protocol before returning success. Failure is terminal for this token connection rather than a fallback to an unguarded session. Clearing user variables, prepared statements or temporary tables must not clear security state.

CHANGE USER is new authentication. Keep the old guard active while staging the new identity. On failure restore both old context and guard, without refreshing the old deadline. On success validate and atomically install the new guard generation before retiring the previous one. A stale old timer cannot revoke the new generation; an expired old guard cannot be revived by a failed change-user. Tests cover token-to-token, token-to-password and password-to-token transitions with the managed-account policy.

Initially reject session migration for the new plugin in both directions: prevent SHOW SESSION_STATES from issuing a migration credential for a cloud-bound identity, and reject `AuthTiDBSessionToken` when the matched native record is cloud-bound. Do not rely only on a server-side issuance check because a previously issued migration token may still exist. SET SESSION_STATES remains SQL session state, not authentication. Future migration requires a server-signed envelope bound to source/destination Instance, original session deadline and authorization revisions, plus destination policy validation; it is a separate capability.

## Transactions and irreversible work

Revocation must prevent new commands, cancel interruptible work, close the connection and clean up an uncommitted transaction. It cannot undo acknowledged commits. A commit already past an irreversible point may finish while cancellation is in progress; DDL/background work may also outlive the connection. The current connection-liveness checker deliberately excludes COMMIT/ROLLBACK, DDL, ANALYZE, LOAD/IMPORT and some BR operations. Reusing that checker alone does not establish a security cutoff.

Define the initial guarantee as bounded denial of new admission and dispatch, plus observed session termination and best-effort cancellation through native execution semantics. Do not promise “no write after the revocation timestamp” or a hard bound on lock release for an in-flight noninterruptible commit. A stronger transaction-effect fence requires a separate kernel commit protocol and storage-level acceptance, not just connection closure. Audit disconnect outcome separately from transaction/job outcome. Enterprise SQL roles should separately govern long-running administrative job submission; revocation does not silently delete an already accepted durable job.

## Rollout and acceptance

The new profile stays disabled by default. Enabling requires a valid descriptor, local policy, TLS, native capability support and verified token-account grants. Reject `skip-grant-table`/`SkipWithGrant` as an incompatible startup/readiness configuration for this feature: current `ConnectionVerification` returns early in that mode, before native/plugin checks. It must not yield a nil identity that silently falls back to unguarded legacy behavior. A rolling fleet routes token clients only to receivers acknowledging the profile and current key/policy revision. Unsupported builds fail explicitly; they do not fall back to legacy JWT or password. No new unauthenticated HTTP endpoint is needed. If a later authenticated internal endpoint is added under `pkg/server`, update `docs/tidb_http_api.md` in the same change.

Deliver in increments: an isolated existing-token feasibility experiment; strict v1 verifier and policy engine; typed identity/connection guard; reset/change-user/migration protections; then the Regional exchange and fleet rollout. Each integration increment must have real MySQL tests as well as unit tests. The detailed commands, negative oracles and readiness gates are in the ExecPlan. Until those pass, preserve existing password access and do not advertise Cloud-identity database login.
